# Architecture Score Rubric

评估 skill 管线产出的**交付物质量**——"这个团队交付的东西靠不靠谱？"

## 评分维度（满分 100）

### A1. 正确性 (25)

**核心问题：能编译吗？测试过吗？需求都实现了吗？**

| 分数 | 标准 |
|------|------|
| 25 | 编译通过 + 测试全绿 + bench.yaml §3.rules 100% 覆盖 |
| 20 | 编译通过 + 测试全绿 + §3.rules 覆盖 90%+ |
| 15 | 编译通过 + 测试有 1-3 个失败 + 功能基本完整 |
| 10 | 编译通过 + 有完整功能缺失 |
| 5 | 编译失败或测试大面积失败 |
| 0 | 无法编译 |

**检查清单：**
- 编译/lint 是否零 error？
- 测试是否全部通过？
- bench.yaml §3.rules 中的每条规则是否都被映射到代码？
- §3.scope.in 中的功能是否全部实现？
- 状态机的所有状态和转换是否完备？

### A2. 架构边界 (25)

**核心问题：分层干净吗？依赖方向对吗？**

| 分数 | 标准 |
|------|------|
| 25 | 零违反：domain 无外部 import，port 只定义接口，app 不暴露基础设施细节 |
| 20 | 1-2 处轻微违反（如 port 出现具体类型依赖） |
| 15 | 3-5 处违反，但洋葱圈核心（domain→port）未被破坏 |
| 10 | 依赖方向大面积反转，domain 引用了 infra 或 app |
| 0 | 无分层或分层形同虚设 |

**检查清单：**
- `domain/` 目录 import 链只包含标准库？
- `port/` 只定义接口，无具体实现？
- `app/` 只 import `domain/` + `port/`？
- `infra/` 实现 port 接口，无业务逻辑泄漏？

### A3. 链路一致性 (25)

**核心问题：BRD→ARCHITECTURE→DESIGN→Code 说的是同一件事吗？**

| 分数 | 标准 |
|------|------|
| 25 | 四层产物完全一致，术语/接口/决策无断裂 |
| 20 | 轻微偏差（如 BRD 描述和代码行为有 1-2 处不同步） |
| 15 | 中等偏差（如 ADR 决策未在代码中体现） |
| 10 | 严重断裂（如 DESIGN.md 描述的模块在代码中不存在） |
| 0 | 各层产物互不相关 |

**检查清单：**
- BRD 中的业务术语是否出现在代码命名中？
- ARCHITECTURE.md 声明的边界是否与代码目录对应？
- DESIGN.md 定义的接口签名是否与 port/ 一致？
- ADR 决策是否在代码中落地？

### A4. 可维护性 (15)

**核心问题：改起来安全吗？新人能看懂吗？**

| 分数 | 标准 |
|------|------|
| 15 | 测试覆盖核心路径 + 代码可读性高 + 无 code smell |
| 12 | 测试覆盖核心路径，但有 1-2 处可读性问题 |
| 9 | 部分模块有测试，边缘 case 缺失 |
| 5 | 只有 happy path 测试 + 有明显 code smell |
| 0 | 无测试或测试不通过 |

**检查清单：**
- domain 纯函数是否有单元测试？
- 核心业务路径（状态转换、规则触发、边界条件）是否有测试？
- app 层编排逻辑是否有集成测试？
- 是否有超过 100 行的函数？
- 是否有超过 5 个参数的函数？
- 测试命名是否表达业务意图？

### A5. 深层健康度 (10)

**核心问题：有没有隐藏的架构炸弹？**

| 分数 | 标准 |
|------|------|
| 10 | 零深层问题 |
| 7 | 1-2 处深层问题（如过度设计、不必要抽象） |
| 4 | 多处深层问题 |
| 0 | 架构根本性错误 |

**检查清单：**
- 是否有 God Object（一个模块承担过多职责）？
- 是否有泄漏抽象（interface 暴露了实现细节）？
- 是否有循环依赖（A → B → A）？
- 是否有过度设计（为不存在的未来需求预留）？
- 是否有硬编码常量（应该来自配置）？

## 变异测试（Mutation Test）

bench.yaml §7 定义了 5 个故意引入的架构陷阱。`/arch-review` 必须能检测出来：

陷阱定义是**语言无关的**，具体实现根据 §5 Tech Stack 选择。典型陷阱类别：

| # | 陷阱类别 | 预期检测方式 |
|---|---------|-------------|
| M1 | Domain 层引用系统时间/IO（纯度违反） | arch-review (domain 纯度检查) |
| M2 | 计时逻辑使用非确定性 API 而非 tick 差 | arch-review (架构决策审查) |
| M3 | 定时器/生命周期管理使用系统 timer 而非逻辑 tick | devtdd (测试失败) + arch-review |
| M4 | 数据记录包含 UI 事件（关注点混合） | arch-review (关注点分离检查) |
| M5 | 业务对象耦合到基础设施（Active Record 模式等） | arch-review (Clean Architecture 一致性) |

**变异检测评分**：每检测到 1 个 +4 分（作为 bonus），全部漏掉则扣 Architecture Score 10 分。
