# Pipeline Health Score Rubric

评估 **skill 管线自身行为**是否合规。每轮由评估者（运行 benchmark 的人/Agent）在 `/arch-review` 后执行。

## 评分维度（各 ~14 分，满分 100）

### 1. 产物定位合规性 (15)

每个 skill 产出是否严格符合其职责定位？

| 分数 | 标准 |
|------|------|
| 15 | 所有 skill 产出严格符合定位，零越界 |
| 10 | 1 个 skill 有轻微越界（如 BRD 中出现技术选型） |
| 5 | 2-3 个 skill 有越界 |
| 0 | 大面积越界，skill 职责混乱 |

**检查清单：**
- BRD.md 是否只含业务需求，无任何技术决策？
- LANGUAGE.md 是否只含术语定义，无架构设计？
- ARCHITECTURE.md 是否只定义边界和依赖方向，无具体实现？
- DESIGN.md 是否只描述接口和数据结构，无业务逻辑？
- 代码是否只出现在 devtdd 阶段？

### 2. 增量正确性 (15)

每个 skill 应该增量产出，还是覆盖产出？

| 分数 | 标准 |
|------|------|
| 15 | 所有 skill 的增量/覆盖策略正确 |
| 10 | 1 处策略错误（如应增量的做了覆盖） |
| 5 | 2-3 处策略错误 |
| 0 | 增量逻辑完全混乱 |

**检查清单：**
- BRD.md 每轮是否覆盖式更新（非增量追加）？
- ARCHITECTURE.md 是否增量演进（保留旧内容 + 新决策）？
- DESIGN.md 是否增量补充（新模块追加，不删旧模块）？
- 代码是否增量开发（新功能不破坏已有代码）？

### 3. 跨阶段信息传导 (15)

上游产物中的关键信息是否被下游正确消费？

| 分数 | 标准 |
|------|------|
| 15 | 信息零丢失，术语一致性 100% |
| 10 | 1-2 处术语不一致或信息丢失 |
| 5 | 多处信息断裂（如 BRD 术语在 DESIGN 中消失） |
| 0 | 各阶段产物互不引用，信息孤岛 |

**检查清单：**
- LANGUAGE.md 术语是否贯穿到 ARCHITECTURE → DESIGN → Code？
- BRD 中的 Open Questions 是否被后续阶段解答或显式标记为 deferred？
- ADR 决策是否传导到 DESIGN.md 和代码实现？
- BOARD.md References 是否正确指向对应产物？

### 4. 顺序合规性 (15)

skill 是否按依赖顺序执行？前置条件是否被检查？

| 分数 | 标准 |
|------|------|
| 15 | 严格按序执行，前置检查 100% 合规 |
| 10 | 1 处顺序违规或前置检查遗漏 |
| 5 | 多处顺序问题 |
| 0 | 顺序混乱，依赖未声明 |

**检查清单：**
- align → design → detail → devtdd → review 是否严格有序？
- 每个 skill 启动前是否检查了上游 `done` 状态？
- AD 路由时，目标 skill 是否先处理 AD 再继续新任务？
- 看板状态流转是否正确（new → doing → done）？

### 5. 代码质量深度审计 (15)

超越普通 code review，深入检查架构合理性。

| 分数 | 标准 |
|------|------|
| 15 | 零深层问题 |
| 10 | 1-2 处深层问题（如过度设计、不必要抽象） |
| 5 | 多处深层问题 |
| 0 | 架构根本性错误 |

**检查清单：**
- 是否有 God Object（一个结构体承担过多职责）？
- 是否有泄漏抽象（interface 暴露了实现细节）？
- 是否有循环依赖（A → B → A）？
- 是否有过度设计（为不存在的未来需求预留）？

### 6. Skill 自身规范合规性 (15)

每个 skill 是否遵守了自己的 SKILL.md 声明？

| 分数 | 标准 |
|------|------|
| 15 | 所有 skill 严格遵守自身 SKILL.md |
| 10 | 1 个 skill 有轻微违反 |
| 5 | 2-3 个 skill 有违反 |
| 0 | 大面积违反 SKILL.md 声明 |

**检查清单：**
- arch-align 是否每次只问一个问题？是否拒绝跳过？
- arch-design 是否在 NFR 对话中探询技术（而非从 BRD 提取）？
- arch-detail 是否检查了上下游一致性？
- devtdd 是否严格按红-绿-重构循环？
- arch-review 是否给出了明确的分数 + 理由？

### 7. AD 闭环完整性 (10)

Architecture Discrepancy 是否被正确路由、追踪、关闭？

| 分数 | 标准 |
|------|------|
| 10 | 所有 AD 被正确路由到目标 skill，闭环率 100% |
| 7 | 1-2 个 AD 路由错误或未闭环 |
| 3 | 多处 AD 丢失或未追踪 |
| 0 | 无 AD 管理机制 |

**检查清单：**
- AD 是否路由到正确的目标 skill？
- 目标 skill 是否在 next doing 时优先处理 AD？
- AD 修复后是否在 EVOLUTION.md 中标记为 resolved？
- 是否有 stale AD（长期未处理的）？
