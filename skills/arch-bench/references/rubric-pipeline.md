# Pipeline Health Score Rubric

评估 **skill 管线协作行为**是否合规——"这些 skill 作为一个团队协作得好不好？"

与 Architecture Score（评产物）不同，Pipeline Health 评的是 **skill 的行为模式**。

## 评分维度（各 20 分，满分 100）

### P1. 产物定位合规 (20)

**核心问题：每个 skill 只产了自己该产的东西？**

| 分数 | 标准 |
|------|------|
| 20 | 所有 skill 产出严格符合定位，零越界 |
| 15 | 1 个 skill 有轻微越界（如 BRD 中出现技术选型） |
| 10 | 2-3 个 skill 有越界 |
| 0 | 大面积越界，skill 职责混乱 |

**检查清单：**
- BRD.md 是否只含业务需求，无任何技术决策？
- LANGUAGE.md 是否只含术语定义，无架构设计？
- ARCHITECTURE.md 是否只定义边界和依赖方向，无具体实现？
- DESIGN.md 是否只描述接口和数据结构，无业务逻辑？
- 代码是否只出现在 devtdd 阶段？

### P2. 增量正确性 (20)

**核心问题：该覆盖的覆盖、该追加的追加？**

| 分数 | 标准 |
|------|------|
| 20 | 所有 skill 的增量/覆盖策略正确 |
| 15 | 1 处策略错误（如应增量的做了覆盖） |
| 10 | 2-3 处策略错误 |
| 0 | 增量逻辑完全混乱 |

**检查清单：**
- BRD.md 每轮是否覆盖式更新（非增量追加）？
- ARCHITECTURE.md 是否增量演进（保留旧内容 + 新决策）？
- DESIGN.md 是否增量补充（新模块追加，不删旧模块）？
- 代码是否增量开发（新功能不破坏已有代码）？

### P3. 跨阶段信息传导 (20)

**核心问题：术语和信息从头到尾没丢？**

| 分数 | 标准 |
|------|------|
| 20 | 信息零丢失，术语一致性 100% |
| 15 | 1-2 处术语不一致或信息丢失 |
| 10 | 多处信息断裂（如 BRD 术语在 DESIGN 中消失） |
| 0 | 各阶段产物互不引用，信息孤岛 |

**检查清单：**
- LANGUAGE.md 术语是否贯穿到 ARCHITECTURE → DESIGN → Code？
- BRD 中的 Open Questions 是否被后续阶段解答或显式标记为 deferred？
- ADR 决策是否传导到 DESIGN.md 和代码实现？
- BOARD.md References 是否正确指向对应产物？

### P4. Skill 自身规范合规 (20)

**核心问题：每个 skill 遵守了自己的 SKILL.md 吗？**

| 分数 | 标准 |
|------|------|
| 20 | 所有 skill 严格遵守自身 SKILL.md |
| 15 | 1 个 skill 有轻微违反 |
| 10 | 2-3 个 skill 有违反 |
| 0 | 大面积违反 SKILL.md 声明 |

**检查清单：**
- arch-align 是否每次只问一个问题？是否拒绝跳过？
- arch-design 是否在 NFR 对话中探询技术（而非从 BRD 提取）？
- arch-detail 是否检查了上下游一致性？
- devtdd 是否严格按红-绿-重构循环？
- arch-review 是否给出了明确的分数 + 理由？
- 所有 skill 是否正确更新了 BOARD.md？

### P5. AD 闭环完整性 (20)

**核心问题：Architecture Debt 被追踪和关闭了吗？**

| 分数 | 标准 |
|------|------|
| 20 | 所有 AD 被正确路由到目标 skill，闭环率 100% |
| 15 | 1-2 个 AD 路由错误或未闭环 |
| 10 | 多处 AD 丢失或未追踪 |
| 0 | 无 AD 管理机制 |

**检查清单：**
- AD 是否路由到正确的目标 skill？
- 目标 skill 是否在 next doing 时优先处理 AD？
- AD 修复后是否在 EVOLUTION.md 中标记为 resolved？
- 是否有 stale AD（长期未处理的）？
- 首轮执行时如无 AD 产生，此维度按满分处理（arch-review 是最后一步，AD 留给下轮）
